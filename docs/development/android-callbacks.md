# Actual Android callback and edit loop

The fifth [GPL patch](../../clients/android/patches/series) extends the semantic adapter with
callback keyboards, actual inline-button input and live message edits. A separate real bot now
receives a callback generated by the pinned Android client, survives a controlled kill before
handling it, edits and answers the query, and acknowledges delivery. The existing `ChatActivity`
shows the edit and keyboard removal, including after a client cold restart. This is a bounded
private-chat interaction loop; the wider foundation acceptance remains open.

## Profile and boundary

Use the approved [toolchain](../../clients/android/toolchain.json): Telegram Android 12.10.1,
revision `62b56a07ca7e30e39f7fd00a6728d6bbd716ca1c`, TL layer 229, Emulator 37.1.11 and AOSP
API 36 default x86_64 revision 2. The dedicated guest uses KVM, two virtual CPUs, 2 GiB RAM,
320×640 at 160 dpi, the default client theme/fonts, English client locale and Persian/English
message content. Guest system time and animation timing are not deterministic world time.

The software GPU mode is now `swangle`: SwiftShader through ANGLE. The guest's SurfaceFlinger
report must identify both ANGLE and SwiftShader. The earlier plain-text evidence used the legacy
`swiftshader` mode; it is a separate graphics profile, not a pixel-equivalence baseline.
[Android documents the software modes](https://developer.android.com/studio/run/emulator-acceleration).
The approved proposal selected an explicit software GPU; this change preserves the app, emulator,
image and display pins. No host GPU or personal desktop/device is used.

The [process boundary](runtime-boundary.md), native guards, restricted startup and authenticated
numeric local HTTP endpoint remain mandatory. Runtime execution has only loopback in its parent
network namespace. Dependency provisioning is separate. The trusted bot fixture still shares the
supervisor's run data mount; separate component filesystem access and quotas remain unfinished.

## Translation and lifecycle

`GramLabBridge` translates callback-only keyboards into the pinned layer's inline row/button/type
objects and preserves `edit_date`. Java owns all TL conversion; the MIT core exposes only the
[independent semantic contract](client-bridge.md).

A real `getBotCallbackAnswer` request validates the private peer, message and UTF-8 data, creates
one request ID and posts to the authenticated callback endpoint. It polls that query's answer
with a bounded wait and completes the original client callback on the existing stage queue.
Supported answers contain text, `show_alert` and zero cache time. Games, passwords, URLs and
answer caching are explicitly unsupported. The wait is an adapter deadline, not a claim about
Telegram query expiration. Cancellation suppresses completion; it does not yet interrupt an
in-flight HTTP call or persist a client command across process death.

A separate worker reads ordered world events. It translates message creation/edit events and
applies them through the unchanged `MessagesController.processUpdateArray` semantic difference
path. Empty polls do not rewrite controller users. The global journal cursor is never assigned
to Telegram `pts`, `pts_count` or `seq`. Unsupported participant changes stop cursor advancement
with an explicit diagnostic; live participant reconciliation remains open.

On restart, the client takes an authoritative snapshot and seeds the existing dialog cache.
This test establishes recovery of the latest edited message in one private chat. It does not
establish recovery of every older cached message, a durable atomic replica cursor, or recovery
after every possible partial bot mutation. The [world callback tests](callback-world.md) cover
stale data, duplicate requests, wrong actors, byte limits and concurrent/reopened retries.

## Behavioral evidence

The contained scenario uses actual HTTP and a separate bot executable. It:

1. Sends `سلام hello`; the bot returns `سلام hello — choose` with `تأیید ✓` / `confirm`.
2. Waits for the messages and accessible inline button, captures the actual screen and bounds,
   and injects an ordinary tap into that dedicated guest.
3. Observes the resulting callback, kills the bot after receipt but before mutation, then starts
   a fresh bot process which receives the same pending update.
4. Verifies the exact edited history, durable answer, empty acknowledged outbox, visible
   `تأیید شد ✓`, removed keyboard and completed Android callback.
5. Force-stops and cold-launches the Android client, verifies the edited bubble exactly once,
   and checks that the guest has zero Android accounts.

Simulation-only and Android modes reuse the same bot/world scenario and compare the same complete
message history and callback answer. The Android mode supplies actual input; it does not create
the callback through a test-only world mutation. UI XML, screenshots, launch records and redacted
adapter traces stay in ignored artifacts. These are local model and rendering observations, not
external Telegram conformance evidence.

The initial four-patch APK rejected the new keyboard schema. After keyboard translation, the
button rendered and a tap reached an explicit unsupported callback response. Adding dispatch and
events exposed a native emulator `SIGSEGV`: post-tap ADB failures initially obscured the cause.
Core inspection located the fault in generated graphics code; the legacy software graphics
libraries were active, with insufficient symbols to identify the exact shader function. Skipping
empty controller updates did not cure the crash. Using SwiftShader through ANGLE allowed the
complete callback/edit/restart test to pass. The actual before, edited and restarted screens were
reviewed; the edited screen also displayed the bot's callback-answer notification.

The final Android gate on 2026-09-06 passes all eight tests, including existing local/external
networking, native rejection, semantic bridge and startup identity checks. Observation fixes wait
for complete history and decode XML line breaks; they do not relax message assertions. Fresh
five-patch preparation reproduces both adapter inputs and dependency metadata, preserving 6,666
upstream UI/resource files byte-for-byte. The contained offline build and APK v1/v2 signature
checks pass; the restricted application manifest and two x86_64 native libraries were inspected.
The local evidence APK has SHA-256
`34f14e43bfe94fd86943fdc47b98e2f145d66aa50767d0f8e76f366d7403af54`.
This identifies the tested artifact, not a reproducible release or distribution approval.
The separate core gate passes 34 tests with 91.47% statement coverage. Python lint/format and
strict typing, Nix/direnv/workflow checks, local Markdown links and public-tree privacy checks pass.

## Reproduction

Prepare/build the full queue using the [contained build procedure](android-build.md), then set
`GRAMLAB_ANDROID_PROBE_APK` to that local APK. Run the focused test in the documented outer guard:

```sh
nix develop .#android --command unshare --user --map-root-user --net bash -eu -c '
  ip link set lo up
  test ! -e artifacts/android-callbacks
  .venv/bin/pytest tests/test_android_callbacks.py --basetemp=artifacts/android-callbacks
'
```

Run the complete Android gate with `-m android` and a fresh artifact directory. Run the separate
core/coverage and static checks in [CONTRIBUTING.md](../../CONTRIBUTING.md). The full goal still
includes client text writes, richer messages/media, broader replay and faults, component mounts,
Mini Apps, compatibility inventory, reports and corresponding-source/license audits. Unknown
operations must retain explicit failures, and no remote publication is authorized.
